# Deploy and publish are independent; deploy adapter owns runtime metadata

> Full architectural model + foundational checks live in [`.claude/rules/design-deploy.md`](../../.claude/rules/design-deploy.md). Phased implementation cuts in [`.claude/rules/design-deploy-implementation.md`](../../.claude/rules/design-deploy-implementation.md). This ADR captures four interlocking load-bearing decisions; the design doc captures everything else.

Closes [#203](https://github.com/gazetta-studio/gazetta-studio/issues/203).

`gazetta publish` and `gazetta deploy` are independent operations on the same target. Neither calls the other; neither gates on the other. Some deploy adapters read from `target.storage` at deploy time (GitHub Pages, S3 static, Netlify static — the deploy IS the upload); others don't (Cloudflare Workers — deploys the worker code; bytes were written to R2 by a separate `gazetta publish`). Operators sequence the two commands based on what their platform needs.

The `target.worker` field is deleted. `target.deploy?: DeployAdapter` is the only field carrying platform glue. Worker-bundling adapters (Cloudflare Workers, Cloudflare Pages + Functions, Vercel Edge, Netlify Edge, Deno Deploy) own both the deploy command AND the runtime binding metadata via a `WorkerCapableDeployAdapter` capability interface that exposes a `workerRuntimeConfig()` method for `gazetta build` to read at build time.

Every target carries `storage:`. `deploy:` is optional and additive. Pure-static hosts (GitHub Pages, S3 static, Netlify static, Azure Blob static, Cloudflare Pages plain-static) wire `filesystemStorage()` + a deploy adapter that reads from it at `execute()` time. Worker-deploy targets wire a real storage provider (R2, S3, Azure Blob) + a worker-deploy adapter; the worker reads from storage at request time, decoupled from the deploy step.

Container deploys (Fly.io, Cloud Run, Railway, Render, AWS App Runner, Azure App Service) do not ship as Gazetta adapters. `gazetta serve` is the runtime inside the container; platform CLIs (`flyctl`, `gcloud`, `railway`, `render`) handle the deploy step from CI or local machine. Gazetta is never invoked at the deploy step for container hosts. This is a permanent shape decision, not a deferral — wrapping platform CLIs that already do the job adds maintenance burden without earning Gazetta-side value.

We picked publish/deploy independence over the Vercel/Netlify-style "deploy implies publish" pattern because the two-phase model matches what Gazetta actually is — content lives in targets independently of platform glue, and the daily command is `gazetta publish`. Auto-publish from deploy would hide the two-phase model, surprise operators when `gazetta deploy` re-renders 1000 pages, and prevent deploying a specific past snapshot.

We picked `target.deploy` replacing `target.worker` over keeping both fields because two fields doing related things violates the "single canonical syntax" rule from ADR-0008 — operators would have to learn "set the bucket binding here or there." The Cloudflare adapter naturally owns BOTH the deploy command AND the runtime binding shape; bundling them in one factory call is honest. The `WorkerCapableDeployAdapter` capability interface handles the worker-bundling concern without forcing non-worker adapters (GitHub Pages, S3 static, Netlify static) to think about workers — same pattern as `BinaryCapableStorageProvider` in `design-media-implementation.md`.

We picked separate `storage:` and `deploy:` fields over "deploy subsumes storage for pure-static hosts" because the per-target `.gazetta/` namespace (per `design-publishing.md`) is the locked invariant — every target needs a real storage location for its sidecars + history. Bundling them would force "set `storage:` here but not there" teaching friction and break history. Slight verbosity (two factory calls for a pure-static target instead of one) is the right trade for conceptual clarity.

We picked no container deploy adapters over per-platform or generic container adapters because platform CLIs already deploy containers well, and Gazetta has no special knowledge to inject between `docker push` and the platform-side orchestration. A `flyDeploy()` wrapper that just runs `flyctl deploy` is the "stub-that-throws" anti-pattern from `team-preferences.md` rule 18 — interface conformance without Gazetta-side value. The honest shape: `gazetta serve` is the runtime; platform CLIs are the deploy mechanism; docs (#213) cover the recipes.

## Consequences

Operators with existing `target.worker` config migrate per the migration section in `design-deploy.md`. Hard cutover per ADR-0005 precedent; pre-1.0 product; no coexistence period; no `gazetta migrate-deploy` CLI. The migration is small (`worker: { type: 'cloudflare', name, bucket }` → `deploy: cloudflareWorkersDeploy({ apiToken, accountId, name, bucket })`) but explicit (the deploy adapter requires `apiToken` and `accountId` as factory args, not just implicit env-var reads).

`gazetta deploy production` runs `target.deploy.execute(ctx)` without checking whether `gazetta publish production` has been run. Adapters that need published bytes (static-host adapters) error clearly at `execute()` time when storage is empty: `DeployContentError`. Operators see the issue immediately and run `gazetta publish` first. CI scripts compose explicitly: `gazetta publish && gazetta deploy`.

Operators deploying to a container host configure `target.storage` + `type:` (`'esi'` or `'dynamic'`) and leave `target.deploy` unset. The `target-deploy-coverage` validator emits info-severity issue at `gazetta validate`: "Target 'production-fly' has type: 'esi' but no `deploy:` configured. Container deployments use platform-native tooling; see [docs/container-deployment.md]." The info severity (not warning, not error) communicates "this is expected for some setups" without nagging.

Target-type compatibility is enforced structurally — adapters declare `supports: readonly TargetType[]`; the `deploy-target-type-supported` validator runs at `cli` + `pre-publish` stages with error severity. Incompatible combinations block the publish, not just warn. Plugin authors writing a new adapter declare their supported target types explicitly; mismatches fail at edit time (TypeScript) + at validate time (validator) + at publish time (pre-publish gate). Three of the four "capability-gap UX" surfaces from `feature-design-process.md` non-foundational disciplines; the fourth (author-time modal) doesn't apply to deploy because it's an operator-tier feature.

No audit event for deploy invocation in v1 (deploy is infrastructure operation; platform-native deploy logs are the forensic record). No `beforeDeploy` / `afterDeploy` hooks in v1 (no first consumer to drive the contract; CI-step workaround covers known use cases). Both deferred with explicit triggers in `design-deploy-implementation.md` — `action: 'deploy'` is a closed-enum extension that lands additively when compliance ask surfaces; hook lifecycle lands when a concrete first consumer emerges.

`gazetta serve` is unchanged by this design — it remains the runtime for self-hosted and container deployments. The contract clarifies that `gazetta serve` is the right answer for container hosts; the docs guide (#213) makes the recipe explicit; the validator surfaces the configuration choice.

Downstream deploy adapters (Cloudflare Pages + Functions, Vercel Edge, Netlify static, GitHub Pages, etc.) each ship as their own small PR after the v1 contract lands. The Onboarding sprint in `ROADMAP.md` ships three priority adapters within 3-4 weeks of the contract. The plugin extension surface (per ADR-0008 + ADR-0009) means npm-distributed deploy adapters work without any plugin runtime registration — operators import + invoke the factory; the field accepts the returned instance.
