# Skill is one prompt body, three invocation modes

> Full design lives in [`.claude/rules/design-code-review.md`](../../.claude/rules/design-code-review.md). Phased implementation in [`.claude/rules/design-code-review-implementation.md`](../../.claude/rules/design-code-review-implementation.md). Glossary entry at [`.claude/rules/dev-glossary.md`](../../.claude/rules/dev-glossary.md) under "Skill". This ADR captures the load-bearing decision; the design doc captures everything else.

A **Skill** is one prompt body with defined input + output contracts, invokable in three modes from the same SKILL.md file:

- **Interactive** — user types `/<name>` in a Claude Code session; the skill walks them through a process step by step.
- **Headless** — a Bot orchestrator passes the skill's prompt body to `claude -p` non-interactively; the orchestrator parses structured output (JSONL findings fence, `VERDICT:` line, etc.).
- **Sub-agent** — another Claude session spawns the skill via the `Skill` tool (the canonical skill-invocation surface) or, when the skill is registered as an agent subtype, via the `Agent` tool; output appears as that agent's final message; the parent session consumes it.

The same SKILL.md serves all three modes. The skill's input + output contract is mode-agnostic — what the skill emits to stdout (prose + structured fence) is identical whether the caller is a human terminal, a bot's `claude -p` invocation, or a parent Claude's `Agent` tool. The skill body never branches on "am I running interactively or headlessly."

We picked this over keeping the previous narrow definition (Skill = interactive-only; user types `/<name>`) because the previous definition couldn't describe what we were already building. Anthropic's `pr-review-toolkit` plugin ships six skills that are invoked both interactively and from each other (the `review-pr` slash command spawns the other five as sub-agents); our own `bots/fix-bot/prompts/reviewer.md` and `bots/dead-code-watcher/prompts/reviewer.md` are reusable prompt bodies invoked headlessly from bot orchestrators; the new code-review skill family needs to be invokable from all three contexts to serve the locked four-consumer surface (local CLI, PR-comment workflow, fix-bot reviewer, autonomous review-bot). Either we broaden Skill to cover what these artifacts actually are, or we invent a new term for an artifact that's structurally identical to a Skill except for which contexts invoke it. Inventing a new term ("Review module" / "Prompt") would have added 7+ glossary entries without distinguishing capability — same file path conventions, same SKILL.md format, same Claude Code skill-discovery infrastructure (`/<name>` slash command, marketplace plugins). Broadening fixes the contradiction at one well-known anchor.

We picked broadening over splitting Skill into two adjacent terms ("Interactive skill" + "Headless skill") because the same SKILL.md serves all modes — the prompt body doesn't change based on invocation context. Splitting one concept into two terms purely on invocation grounds would create a permanent "is this an interactive skill or a headless skill?" question for every new artifact. Mode is a property of the invocation, not of the skill.

We picked the narrow term "Skill" (broadened in scope, kept as the name) over a more abstract term ("Prompt artifact" / "Reusable prompt") because Claude Code's first-party documentation, the marketplace plugin format, and `~/.claude/skills/<name>/` filesystem convention all use "Skill." Diverging from upstream vocabulary would force every contributor to learn a project-local term for a thing the broader ecosystem already names.

We picked one definition over consumer-tagged variants (e.g., `Skill: bot-only` / `Skill: interactive-only` per SKILL.md frontmatter) because the four-consumer surface explicitly requires every code-review angle skill to be invokable from all three modes. Tagging a skill as "interactive-only" would force a duplicate "headless" version of the same prompt body — duplication of judgment.

## Consequences

The dev-glossary entry now defines Skill as "reusable prompt body, three invocation modes." Future skills (code review, future families) follow this shape. The glossary entry's example pairing notes that interactive skills (like `triage`) and autonomous bots (like `triage-bot`) cover the same domain at different audiences — the interactive `review-orchestrator` skill and the autonomous `review-bot` will do the same.

The producer/consumer rule from [`bots/README.md`](../../bots/README.md) determines what work belongs in the skill body (Claude judgment) vs the invoking orchestrator (deterministic parsing). A skill that requires its caller to perform deterministic parsing of natural-language output is mis-shaped — emit structured output (JSONL fence, `VERDICT:` line, marked sections) and let the orchestrator parse it via regex/JSON.parse. This rule applies uniformly across all three invocation modes; an interactive user reads the structured fence the same way a bot's orchestrator does (humans can scan a small fenced block; orchestrators parse it).

A skill's frontmatter (`name`, `description`, `allowed-tools`, `argument-hint`) is the contract surface for interactive invocation (the user's slash-command UX comes from the frontmatter). The same frontmatter is read by sub-agent invocations (the `Agent` tool's description matching). Headless `claude -p` invocations also read frontmatter but care less about `argument-hint` since the orchestrator constructs arguments programmatically. None of these consumers re-write frontmatter; one source of truth.

Skills can spawn other skills as sub-agents (mode #3). The `review-orchestrator` skill spawns each angle skill (`review-diff`, `review-security`, etc.) via the `Skill` tool with the angle name. This composition relies on the spawning Claude session having `Skill` tool access; we accept the constraint and document it in `review-orchestrator/SKILL.md` `allowed-tools`. Skills that aren't intended to be composed don't need `Skill` in their allowed-tools. Bots invoking skills headlessly (per `bots/_lib/claude.ts`'s `--allowedTools` budget) include `Skill` in their tool list when they need to spawn skills — e.g., fix-bot's reviewer (Agent B) lists `['Bash', 'Read', 'Skill']` to invoke `review-architecture` and conditionally `review-security` per `design-code-review.md`.

Existing bot reviewer prompts (`bots/fix-bot/prompts/reviewer.md`, `bots/dead-code-watcher/prompts/reviewer.md`) are arguably Skills under the broadened definition — reusable prompt bodies with defined contracts, invoked headlessly. We intentionally don't migrate them to `.claude/skills/` in this design pass; their `bots/{bot}/prompts/` location keeps them co-located with their bot-specific orchestrator and per-bot tests. A future cleanup could move them; the broadened definition opens the door without forcing the migration.

Plugin authors shipping a Skill write `SKILL.md` under either `.claude/skills/<name>/` (project-level, versioned with the repo) or distribute a Claude Code marketplace plugin (cross-project). No `package.json` ceremony, no registry; Claude Code's skill-discovery infrastructure picks up the file based on path convention. Operators or maintainers wanting a custom angle for the code-review family drop a `.claude/skills/review-{custom}/SKILL.md` into the repo and extend the dispatch table; the orchestrator picks it up on next invocation.

Migration cost is zero — the previous narrow definition wasn't materially enforced; existing `~/.claude/skills/` files already cover skills that span multiple invocation patterns in practice. Codifying the broadening lets future design docs reference "Skill" without ambiguity.

If a future Claude Code feature splits skills into invocation-mode-specific subtypes (e.g., upstream documentation introduces "interactive-only skills" as a distinct file format), this ADR's broadening is forward-compatible — the project's locked definition would be a superset; we'd document the upstream subset as a constraint on specific skills that opt into it.
