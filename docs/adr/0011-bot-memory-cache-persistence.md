# Bot reviewer-log persisted via GH Actions cache; compactor truncates

> Full architectural model for the bot memory system lives in [`bots/README.md`](../../bots/README.md) ("Durable memory" + "Reviewer-log persistence" sections) and the per-bot design comments inline in `bots/{bot}/reviewer-log.ts`. This ADR captures three interlocking load-bearing decisions about the reviewer-log surface specifically.

Each bot's `reviewer-log.jsonl` — the append-only record of every Agent B verdict (APPROVE / REJECT / NEEDS_HUMAN) — is persisted across runs via `actions/cache@v4`, not committed to `main` and not uploaded as an artifact. The bot reads the cache at workflow start (via `actions/cache@v4`'s native restore step), appends new verdicts during the run, and the same cache step saves the file on the workflow's post-step. The cache key is `{bot-name}-reviewer-log-v1`; bump the suffix if the JSONL schema ever changes.

Daily-bot workflows (`dead-code-watcher.yml`, `fix-bot.yml`) and the monthly compactor workflow (`bots-compact.yml`) share a single concurrency group per bot (`group: dead-code-watcher`, `group: fix-bot`) with `cancel-in-progress: false`. Concurrent runs queue rather than race — the load-bearing invariant for cache safety is "exactly one writer to the cached file at any time."

The monthly compactor reads the reviewer-log, produces its lessons-learned rewrite (committed via PR per the existing flow), then truncates the file to a bounded window (`REVIEWER_LOG_KEEP_LAST = 200` by default — twice the read window). The compactor IS the memory-trimmer for this surface; daily bot appends grow the file, monthly compactor prunes it. Truncation only fires when Claude succeeds — a failed run preserves the full log so next month's retry has the same input.

We picked cache-based persistence over per-run PR-to-main because the reviewer-log is operational signal, not the forensic record. The forensic record is the audit log (per `design-audit.md`) and the bot's transcripts artifact (per the existing `Upload transcripts` step). Reviewer-log entries are raw input the compactor reads to produce lessons-learned and skip-list glob rules — committing every append to `main` would be PR-noise without forensic value, and the project's rule 33 ("every change to main goes through a PR") was written about code changes, not bot-produced operational state. The compactor's lessons-learned rewrites DO go through PR (one per month, holistic, reviewable); raw verdicts don't need that treatment.

We picked GH Actions cache over `actions/upload-artifact@v7` because the compactor's access pattern reads `tailReviewerLog(path, 100)` — only the last 100 entries inform the next month's lessons. Cache restores the whole file at workflow start (~1 second) in shape ready to consume; artifacts would require per-run `gh run download` + concatenation + slicing across N artifacts to recover the same view. The 7-day cache eviction window is effectively-infinite under daily-bot cadence: every daily cron touches the cache and resets the timer. If a bot is broken for 7+ days the cache is gone — but at that point the persistence model is the smaller problem.

We picked compactor-truncates over compactor-read-only because the compactor's job IS memory compaction, and leaving the reviewer-log uncompacted while every other memory surface (`lessons-learned.md`, `skip-list.json` rules for dead-code-watcher) gets compacted was an inconsistency masquerading as a design. `tailReviewerLog(100)` already imposes a working-window bound at read time; truncating the underlying file makes that bound explicit and keeps the cached blob small across many months of runs. Old entries are intentionally dropped — git history would have been the long-term archive but the cache-based persistence model trades archive depth for operational simplicity. If raw-history preservation ever earns its keep, a future artifact-upload step alongside the cache step is the additive answer; deferred until concrete demand surfaces.

We picked workflow-level `concurrency:` group enforcement over advisory locking (e.g. a `.lock` file in the cache) because GH Actions ships first-class single-instance enforcement and we don't need to invent our own. The literal group name (`dead-code-watcher`, not `${{ github.workflow }}`) is the load-bearing detail: it lets the monthly compactor's matching job in `bots-compact.yml` share the same concurrency group as the daily workflow, so the compactor and the daily bot cannot run concurrently. `cancel-in-progress: false` (queue, don't cancel) preserves any in-flight Agent A/B work — the compactor will simply wait.

## Consequences

Reviewer-log entries are bounded by the cache's last-N policy (default 200 entries after a successful compaction). At ~5 verdicts/day for the dead-code-watcher weekly cron, this represents ~40 weeks of recent verdicts — more than enough context for the monthly compactor's pattern surfacing. For fix-bot's daily cadence, 200 entries is ~40 days of input. Both well-bounded; both retain meaningful cross-run signal.

A bot that runs for more than 7 days without any cron firing (paused workflow, repo archived, etc.) loses its reviewer-log. The cache eviction is silent. Recovery: the next run reads an empty file (cache miss) and `tailReviewerLog` returns `[]`; the bot continues normally. Lessons-learned.md remains in the repo so Agent A's prompt is unchanged; only the raw signal is gone until new verdicts accumulate.

The cache key is per-bot — `dead-code-watcher-reviewer-log-v1` and `fix-bot-reviewer-log-v1`. Cross-bot cache isolation is structural (different keys); the project's "bots should have separate memory" rule holds at the cache layer too.

Local development of bots (running `npm run dead-code-watcher` outside CI) writes `bots/{bot}/reviewer-log.jsonl` to the local filesystem. The path is in `.gitignore` — local files never accidentally commit. Local files don't sync with the CI cache; CI's cache is its own world. Developers iterating on prompts via `npm run replay` (per `bots/README.md`) get a fresh in-process file each time, which is the right shape for prompt iteration.

If a bot's prompt or `ReviewerLogEntry` schema changes incompatibly, bumping the `-v1` cache key suffix (e.g. to `-v2`) is the migration path. Old entries are stranded in the v1 cache (auto-evicted in 7 days); v2 starts empty. No data migration; the entries are operational signal, not durable record. The schema is intentionally small (timestamp + verdict + reasoning + summary) to make this kind of cutover easy.

The compactor's prune-only-on-success behaviour means that a sequence of failed compactor runs (Claude rate-limited, transcript corrupted, etc.) leaves the reviewer-log growing across months instead of staying bounded. Each daily-bot append still adds an entry; pruning waits for a successful compactor run. In the worst case this is bounded by 5 verdicts/day × N months between successful compactions; with the existing `continue-on-error: true` workflow posture, a maintainer notices stalled compactor runs via the missing monthly PR.

A future artifact-upload step alongside the cache step would preserve raw verdict history beyond the 200-entry pruning window. Triggers for adding it: an operator reporting they want to debug "what did Agent B say about X six months ago," a compliance ask to retain the audit shape longer than the bot's audit log captures, or evidence that future compactor iterations could benefit from a longer-tail signal. None of these are concrete today; the artifact path is documented as additive and deferred.
